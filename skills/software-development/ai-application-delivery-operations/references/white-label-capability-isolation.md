# White-label capability integration

## Scope

Use when an evaluated repository portfolio is being turned into reusable client offerings. White-label is a proposed architecture until the user approves it, not an inferred requirement from a request to clone repositories or build an activation dashboard.

## Inspection and design

1. Map repositories to client outcomes instead of selling each repository as a separate product. Distinguish portable procedure skills, executable services, model routing, and internal quality tools.
2. Inspect actual authentication middleware, default environment handling, tenant authorization, storage paths, and deployment modes. README claims of organizations or API-key permissions do not establish end-to-end tenant isolation.
3. Prefer dedicated application instances and storage per client for an initial pilot when shared-tenancy boundaries are unproven. A shared code revision is compatible with separate deployments. Branding alone never separates data.
4. Separate brand configuration (name, logo, colors, domain, locale, tone), modules, users/roles, data, credentials, budgets, backups, and version/rollback records. Keep private knowledge and memories out of shared skill packages.
5. Treat Hermes profiles as configuration separation, not an OS security sandbox for agents that can execute commands. Use stronger runtime isolation when client data or untrusted execution requires it. Cursor is a development client, not automatically a customer-facing execution service.
6. Check root licenses, dependency obligations, notices, trademarks and provider terms independently. A code license does not grant rights to source books, documents, datasets, or client content.

## Dashboard and executor boundary

A persisted selection or enabled flag is only catalog state. Until a bounded executor exists, label its action “Request enablement” rather than “Activate.” Once execution exists, retain separate requested, approved, installed, running, connected and verified states, with observed evidence and timestamps.

Never accept arbitrary browser-supplied shell commands. Active security testing stays behind explicit target authorization and isolated execution, not an unrestricted customer button. Do not route all projects through an unproven model gateway merely because it is in the portfolio.

## Minimal acceptance sequence

- Use one internal brand and a second synthetic tenant to test boundaries before external client rollout.
- Verify denial of cross-tenant document, file, API and administrative access, including direct resource URLs. Test missing authentication configuration; it must not silently open the service.
- Test a narrow workflow per enabled module: source-grounded document answers, factual preservation for style skills, authorized-site SEO queries, or model request/fallback behavior.
- Verify actual invocation separately in Hermes and Cursor. Copying reviewed skill files is not client integration proof.
- Test export, deletion, backup restoration and rollback with synthetic data. Disabling a service must not delete client data implicitly.
- Show a real end-to-end demonstration before promoting the next module. Budget and human approvals remain explicit for provider calls, submissions, publishing and security scans.

## Evidence discipline

Record repository-specific findings with inspected revision and source location in the project dossier; recheck them before implementation. Do not fossilize a particular project's current password model, cloud mode, or license version as a permanent fact in this procedure.

The CapabilityLab discussion surfaced the distinction between shared-password access, organization-aware tenancy and API-key permissions. These are inspection questions for every new deployment, not interchangeable guarantees. No claim that those repositories are now deployed or isolated follows from the discussion.
