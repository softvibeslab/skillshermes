# Multiniche digital-growth profile design

Use this reference when specializing a Hermes profile that must audit digital presence across several niches, research markets and competitors, design conversion landings, recommend funnels, and operate a measurable improvement loop.

## Core design decision

Do not define the profile as a generic “marketing expert that knows everything.” Define one invariant operating system and let niche variables change the recommendation:

`evidence → diagnosis → positioning → funnel → landing/assets → measurement → iteration`

The invariant is the method. The variable layer is business type, geography, sales motion, consideration level, conversion event, available proof, regulation, channel access, and operating capacity.

## Profile specialization workflow

1. Inventory capabilities twice:
   - all skills available to the source/current Hermes profile;
   - skills and toolsets actually present in the fresh target profile.
   Do not assume local or agent-created skills were copied into a fresh profile.
2. Check the target profile's enabled toolsets and configured MCP servers before promising integrations.
3. Classify relevant capabilities by job:
   - research and evidence;
   - social/public-presence audit;
   - landing/UX/copy;
   - implementation/version control;
   - distribution/operations;
   - measurement/evaluation.
4. Separate the deliverables:
   - `SOUL.md`: identity, invariant method, evidence rules, guardrails, routing rules, output contract;
   - `USER.md`/memory: durable brand voice, preferred formats, approval rules, sectors, CTAs;
   - umbrella skills: repeatable procedures;
   - references: source-specific API notes and research banks;
   - MCP/config: actual external access.
5. When the target is another active Hermes profile, create a reviewed draft outside its profile directory first unless the user explicitly approved applying it. This avoids silently changing another profile's behavior.
6. Configure and verify one capable model before adding MCP or automation.
7. Test the SOUL against several materially different business cases before treating “multiniche” as validated.

## SOUL architecture

A useful SOUL contains:

1. Identity and outcome: evidence-based growth operator, not generic content generator.
2. Adaptation variables: B2B/B2C, local/digital, service/product/ecommerce/creator/community, purchase consideration, primary conversion, sector constraints.
3. Evidence hierarchy: authorized first-party data → official APIs/docs → public primary sources → reputable secondary sources → interpretation.
4. Claim labels: observed fact, hypothesis, recommendation, unavailable datum.
5. Digital-presence scorecard: discoverability, relevance, trust, conversion, content, demand/competition, measurement, retention/referral. Scores require evidence and confidence; avoid false precision when data is missing.
6. Funnel contract: demand signal → channel/content → landing → capture → qualification → follow-up → conversion → delivery → retention/referral.
7. Landing standard: message match, one promise, one primary CTA, real proof only, objection handling, minimal form friction, semantic/accessibility basics, responsive performance, SEO/structured data when relevant, analytics events defined before launch.
8. Improvement loop: baseline, outcome metric, diagnostic metrics, evidence-backed hypothesis, smallest measurable change, result, learning, next action.
9. External-action guardrail: no publishing, outreach, campaigns, account changes, or invented proof without explicit approval.
10. Tool ladder: native Hermes tools and existing skills first; official APIs/CLI next; MCP only when it unlocks a current repeated job.

## Framework selection

Use frameworks as lenses, not mandatory ceremony:

- Jobs To Be Done: customer progress and context.
- STP: segment, target, position.
- Voice of Customer: real language from interviews, reviews, authorized exports, and public sources.
- LIFT/message match: diagnose relevance, clarity, anxiety, distraction, urgency, and continuity from channel to landing.
- Awareness stages: adapt copy to buyer knowledge.
- ICE: rank experiments by impact, confidence, and effort.
- PDCA: run the improvement loop.

AIDA, PAS, and TOFU/MOFU/BOFU are copy/planning aids, not substitutes for evidence.

## Minimal integration stack

Start with capabilities already built into Hermes: web/search, browser, vision, files, code execution, delegation, memory, and cron.

Add only when a real account or repeated workflow exists:

- analytics API/MCP for authorized first-party data;
- browser automation MCP for reproducible QA when built-in browser flows are insufficient;
- Lighthouse/PageSpeed plus an accessibility CLI for landing checks;
- Search Console API through a narrow adapter;
- official social APIs for authorized accounts;
- crawler/extraction MCP for larger public-site research;
- GitHub MCP only when content/landing operations live in repos;
- observability/evaluation only after there are traces and representative cases.

For social platforms, prefer official APIs, owner-provided exports, or permitted public data. Never infer private reach, retention, conversion, or audience demographics from a public profile.

## Common pitfalls

- Copying a long tool catalog into SOUL and expecting tools to exist.
- Installing many overlapping SEO/CRO/research skills before testing one workflow.
- Treating “multiniche” as one universal funnel.
- Scoring missing data as poor performance instead of “not observable.”
- Recommending dashboards, CRM, graphs, or multi-agent orchestration before a repeated need exists.
- Adding both competing observability stacks or redundant browser MCPs at the MVP stage.
- Optimizing the prompt by adding rules indefinitely instead of evaluating representative cases and fixing observed failures.

## Verification checklist

- [ ] Source and target skill inventories were distinguished.
- [ ] Target toolsets and MCP state were checked.
- [ ] SOUL contains method and guardrails, not credentials or unsupported tool promises.
- [ ] Missing local skills are listed as installation/copy steps.
- [ ] Model works end to end before integrations are added.
- [ ] At least several distinct business archetypes were tested.
- [ ] Every audit distinguishes facts, hypotheses, recommendations, and unavailable data.
- [ ] External actions remain approval-gated.
