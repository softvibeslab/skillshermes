# Repository-native assistant kit adaptation

## Source example: AIS-OS

Source: https://github.com/nateherkai/AIS-OS.git
Inspect the current checkout rather than assuming these landmarks remain unchanged:
- `README.md`, `CLAUDE.md`: operating model and upstream assistant assumptions.
- `aios-intake.md`: personal/business intake template.
- `.claude/skills/`: upstream procedures including onboard, audit, level-up, grill-me, 3d-brain, and link.
- `.claude/skills/3d-brain/scripts/scaffold.mjs`: optional UI generation; inspect before execution.

This is an example of a filesystem/context-based assistant kit. Do not infer that every repository needs dependency installation, a database, a bot, or scheduled automation.

## Minimal adaptation sequence

1. Inspect source instructions and executable helpers independently. Identify required runtime versus optional visualization.
2. Create the authorized isolated profile using the installed CLI's documented syntax. `--no-skills` avoids deliberate bulk seeding; inspect actual skills afterward instead of promising absolute isolation.
3. Write repository-grounded identity and a local operating skill. If importing existing upstream procedures, copy their entire resource trees, namespace collisions (for example `ais-audit`), and translate tool and command assumptions. Review internal cross-references, not just YAML names.
4. Use only necessary provider configuration. Model/provider settings do not prove authenticated inference, and copying all runtime configuration can bring unrelated MCPs or messaging credentials.
5. Verify skill discovery and a one-shot chat that loads a relevant skill and cites real repository sources. Advertise only invocation syntax verified in the installed runtime; upstream `/audit` need not be a native Hermes slash command.
6. For an optional graph UI, start with an explicit allowlist of repository documents. Verify graph data, HTTP health, actual listening address, and source traversal protections separately. Inspect what generated pages load externally before describing them as private/offline.
7. Collect personal intake interactively, one question at a time. Business, voice, priorities, communications, documents, revenue systems, and repetitive work are candidate subjects—not facts to invent. Connection inventory is not integration consent.
8. Deliver installed location, verified capabilities, pending gates, and one next action. Distinguish a visual link graph from semantic retrieval or autonomous execution.

## Approval and evidence boundaries

Keep read-only probes, profile mutations, and Git metadata changes in separate calls. The motivating session bundled an HTTP graph probe with skill copies and `.git/info/exclude` writes; the entire command was denied. None of those intended results can be inferred from that call. This is a workflow lesson, not an unresolved software defect.

After denial, stop the affected workflow and wait for fresh authorization. A later request to curate skills permits library maintenance, not resumption of the original installation. Historical summaries can guide discovery but cannot supply fresh runtime verification.

Local Git exclusions reduce accidental staging of untracked intake/generated artifacts; they do not protect already-tracked files or replace secret review before publication.

## Extending an existing project knowledge map

For AIS-OS-style 3D Brain work, inspect the existing `.claude/skills/3d-brain/SKILL.md`, `apps/3d-brain/brain.config.json`, and server/build scripts before changing sources. These are discovery landmarks, not guaranteed paths or a guaranteed configuration schema. Reuse the existing app rather than scaffolding over it and losing history.

1. Resolve each requested project to a source root using current project indexes and relevant session evidence. Historical paths are candidates, not verified directories. Search only the authorized scope; do not recursively scan home or unrelated workspaces.
2. If ambiguity remains, ask one focused question with only evidence-backed alternatives. Do not turn an uncertain brand relationship into an asserted project identity.
3. Inspect real paths and symlink targets before expanding sources. Authorization to map a project does not automatically include an associated Hermes profile's memories, conversations, credentials, or unrelated repositories. Preserve local intake/voice exclusions.
4. Inspect the actual source schema and rebuild/watch behavior. Add the smallest explicit document allowlist and preserve existing categories and graph history. Keep generated private graph data out of publication.
5. Verify separately: configuration parses; sources stay within approved roots; graph generation succeeds; each requested project contributes representative nodes; HTTP responds; listener is loopback-only. Rendering a healthy dashboard does not prove that new sources were indexed.
6. If a check is blocked by approval, report that gate as unverified. Do not use a historical PID, remembered URL, or tool-denial attribution as evidence of current health or a deliberate user rejection.

A repository-native procedure can be read directly without installing a Hermes alias. Registry discovery and repository-file discovery are different checks; report accurately which one succeeded. A compaction summary mentioning a prior read is not a fresh read of the file.

## Completion gates

Report each independently: checkout inspected; profile created; identity installed; skills discovered; authenticated skill-loaded chat passed; optional UI HTTP/bind/source checks passed; personal intake confirmed; integrations explicitly authorized. Do not collapse these into a single 'installed and working' claim.
