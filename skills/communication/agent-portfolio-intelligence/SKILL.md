# Agent Portfolio Intelligence

Use when a mixed portfolio of agents, repositories, products, demos, or collaboration boards must be turned into a decision-ready inventory, strategic assessment, or buyer-facing explanation.

## Class workflow

1. **Set scope and disclosure.** Identify the audience, decision, time-to-understand, source systems, and whether output is generic, portfolio-level, or an approved case study.
2. **Inventory before narrating.** Discover real project/repository roots, configured agents, board object families, and durable source documents. Separate deployable projects from support directories, current evidence from templates/history, and configured/recent/running status claims.
3. **Normalize into business lines.** Group technical profiles and related artifacts into 5–8 understandable capabilities. Keep source provenance, ownership, maturity, evidence, approval boundary, and confidence explicit.
4. **Analyze decision readiness.** Across repositories and boards, extract thesis, actors, deliverables, blockers, metrics, owners, dates, evidence, decisions, risks, and stop conditions. Use `GO`, `EXAMPLE_SLACK_ID GO`, or `NO-GO` when a readiness call is requested.
5. **Communicate from one canonical source.** Lead with role, observable work, evidence, and human control. Derive the smallest useful set of workbook, visual map, infographic, video, demo, landing page, or content roadmap from one approved content model.
6. **Verify claims and artifacts.** Reconcile counts, inspect source provenance, label estimates, test generated files and interactions, search public assets for forbidden names, and distinguish publication from local staging.

## Labeled operating modes

### Workspace and repository inventory

Use evidence-based root discovery, shallow metadata, conservative maturity scoring, category-specific recency, and a validated Excel/CSV catalog. Never treat dependencies, generated output, or support folders as projects.

### Cross-project integration fit

Use when asked where a new API, webhook, or automation belongs across existing projects. Default to read-only assessment, not deployment. Discover roots and apply requested exclusions before reading content; deduplicate clones/worktrees and distinguish products from tools and reference repositories. Report uncovered roots and insufficient evidence instead of claiming exhaustive coverage.

Trace actual input channels and existing persistence before proposing architecture. A WhatsApp CTA is not a mail event, and a static landing is not a working backend. Verify the provider's event and authentication contracts from SDK/schema or official documentation; account authentication alone does not prove mailbox, write, or webhook permissions. Prefer existing backend/CRM components where their ownership and data scope fit, not one integration per repository. An internal project registry is not automatically authorized to store each client's customer records.

Deliver a project/family matrix with use case, prerequisite, human approval boundary, and explicit defer/no-value entries. Recommend one bounded pilot; distinguish observed capabilities, proposals, and untested delivery behavior. For provider details and pilot acceptance gates, load `references/cross-project-webhook-fit.md`.

### Installed skills and repository ecosystem audit

Assess skills and repositories together, not as separate popularity lists. Keep these counts distinct: Git roots, normalized remote origins, product families, catalog-visible skills, and repository-contained skills. A shared remote identifies related checkouts, not necessarily redundant copies; preserve worktrees and experiments. Strip credentials from remote URLs before recording them.

Use an evidence ladder: discovered → documented → configured → callable → end-to-end verified. Report the highest observed level per component; a CLI listing succeeds without proving that its squads or capabilities execute. A skill in a source repository is not necessarily installed in the active profile, and a catalog entry does not establish runtime compatibility.

For each recommended capability, pair repositories with relevant skills and state its role, overlap, missing contract, human approval boundary, and smallest acceptance check. Read connection registries to distinguish planned links from active declarations; neither substitutes for an end-to-end test. Prefer one coordination authority and one bounded pilot over installing several overlapping control planes. Do not install skills or start services during a read-only assessment.

Verify workbook sheets and report claims before delivery. Label discovery coverage separately from deep-read coverage; re-check delegated findings against primary files before presenting them as facts. Keep exact session counts and component snapshots out of durable instructions. See `references/skills-repository-ecosystem-audit.md` for the evidence matrix and delivery checks.

### Collaboration-board decision analysis

Fetch every paginated object family, preserve geometry and hierarchy, classify current/derived/historical/template content, identify the reading path and information-architecture gaps, and prefer a minimal cockpit over destructive rebuilding. Back up and verify before any requested rewrite.

### Portfolio storytelling

Explain capabilities and outcomes rather than profile directories or model names. Consolidate overlapping agents into business lines; every case should state the user goal, work performed, evidence produced, and sensitive decision retained by a person.

### Multiformat capability explainers

Choose the smallest medium that solves comprehension. Build one canonical message and derive infographic, video, demo, page, subtitles, and alt text. Apply disclosure constraints to filenames and metadata as well as visible copy; reject decorative metrics and chat simulations without evidence.

## Cross-cutting safety

- Never expose credentials, private contacts, customer data, or internal names beyond the approved disclosure level.
- Modification time, recent logs, and configuration are not proof of current operation.
- Do not delete source projects or board history merely because an inventory contains duplicates.
- Do not present estimated metrics, simulations, or illustrative cases as measured results.
- Verify every external side effect and public artifact independently.
